# Build plan — IT access-request intake

This is a plan, not an implementation or a report of passing checks. Only planning/plan.md is updated in this task. All source files, fixtures, test names, commands and deliverables described below are planned work. The 89 requirements and 69 research questions in planning/spec.md remain unchanged. A planned test demonstrates only the behavior it actually exercises; mocked extraction does not establish live model accuracy.

## Choices

- **Runtime:** Python 3.10 or later, following the classroom prerequisite and existing unittest starter; the exact supported Python release and dependency versions will be pinned during implementation.
- **Interface:** a CLI using the prospective entry point `python3 -m access_intake`, because operators need intake, queue inspection, retry and resume without a required web deployment.
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests -v`, matching the starter; tests use injected fake configuration, saved responses and controlled clocks/events, never a real key or live network.
- **Provider invocation:** OpenAI, as selected by the person in this session, through the Responses API over an injectable HTTP transport; build the deterministic fixture provider first. Use structured extraction output and exercise the real adapter through fake HTTP responses. The supported model and its settings remain G1.
- **State:** use a transactional store for document revisions, processing attempts and current-result references; select its backend and supported host topology at G2 before implementing concurrency guarantees.
- **Output:** current extraction JSONL and queue JSON are exports of one consistent recorded generation; history is stored separately and linked to its earlier attempt/source. Container details, pending-state presentation and failure provenance await G5.
- **Schema and fixtures:** keep the supplied extraction schema as the contract; choose a compatible validator and lockfile at G3. Hand-author expectations from the evidence catalogue below before writing response fixtures or measuring extraction outputs.

The selected API is grounded in the official [OpenAI Responses create reference](https://developers.openai.com/api/reference/resources/responses/methods/create) and [Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs), checked on 2026-11-13. Plan POST /v1/responses with a configured model and the extraction schema in text.format using json_schema. The non-streaming adapter checks response status, error and incomplete_details before parsing output_text content; a refusal content item is handled separately. Fake envelopes exercise completed output, refusal and incomplete status. Local schema and exact-quote validation still run after provider output is decoded. The model must support the chosen structured-output configuration; no model is inferred from documentation examples.

Implementation gates and questions for review follow the skill's instruction: “Where a spec line is unclear, say so in the plan and ask the person; do not guess a rule.” These are unresolved questions, not additions to the requirements. The person selected OpenAI after being asked about provider/model, source ordering and accuracy counting; the model, ordering and counting answers remain open.

## Steps, in build order

For every step, first write its named tests, run them with API_KEY unset, and record the real failure before implementing that step. If a new test already passes, record that fact and do not manufacture a failure. Only then implement the step and run its tests and the whole suite. Test ownership below is exclusive: later steps run earlier tests for regression but do not claim to introduce them. A failing regression stops progression. No build or verification step requires API_KEY; the real adapter is tested with an injected fake transport. No optional live run is scheduled here.

Add a controllable success/error/delay response mechanism without implementing extraction or routing. **Spec:** R-78. **Done when:** a saved response or requested fake failure is returned reproducibly offline, and the new mock-provider test passes without relying on the existing canned-reply test as proof of application behavior.

### Source-derived expected facts

The following catalogue fixes concrete facts for the supplied examples before any measured output exists. Each F-01–F-20 row refers to that file's decoded message. Expected document_id is the input filename; expected source_sha256 is SHA-256 of its original bytes, independently recomputed from the test input. Every record has the 14 schema keys; all non-enum scalar values are strings or null and supporting_quotes/issues are string arrays.

For each catalogue row, the quoted purpose span is a source-grounded fixture value for business_purpose. It is not a claim that every other faithful prose rendering is wrong; the scoring treatment remains G4. Identity/team, kind, system, environment, permission, dates and manager are anchored by the quoted evidence in that row. Planned supporting_quotes include the relevant exact source spans, with both alternatives mandatory for unresolved conflicts and the attempted instruction retained for overrides. Issues assertions concern the specified missing/conflicting/policy facts, not invented exact wording or array order. Unless a row identifies unresolved facts, no missing/conflicting fact is expected from the quoted complete request. Historical permission mentions do not create unresolved requested-permission conflicts.

Routing abbreviations used only to keep this plan readable are: **OWNER** = (status review, owner System Owner, next_action review-request); **SECURITY** = (review, Security Review, review-risk-then-owner); **CLARIFY** = (needs-information, IT Service Desk, clarify); **WITHDRAW** = (review, IT Service Desk, confirm-withdrawal); **INSPECT** = (review, IT Service Desk, inspect-message); **ERROR** = (error, IT Service Desk, retry-extraction), with extraction null and a failure description. These expand to the literal policy strings in assertions, not new statuses.
